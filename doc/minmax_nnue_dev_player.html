      1The player at a glance

      The player is a classic alpha-beta engine in the style of Stockfish, adapted to Yolah: iterative deepening with aspiration windows, principal variation search, a transposition table, a move ordering that learns during the search, reductions and pruning at the nodes that do not matter, and a small neural network (an NNUE) at the leaves. Each of these parts was added as an option, measured in matches against the previous version, and kept only if it won. This document follows the final configuration.

      All code excerpts are the real code of the repository with two simplifications, so that only what runs in the final player is shown: the search debugger's recording macros (TR(...), TRET(v)) are removed, and the branches of options that are switched off are cut. When a few lines were condensed, the excerpt says so.

      1.1Yolah in one minute

      Yolah is played on an 8×8 board. Each player has four pieces that move like chess queens: any number of free squares in a straight line or a diagonal, never through a piece or a hole. Every move scores one point, and the square the piece leaves becomes a hole for the rest of the game. The board shrinks at every move. A player who cannot move passes. The game ends when neither player can move, and the player with more points wins, so the winner is the one who made more moves. Black moves first.

      Two consequences shape the whole engine. There are no cycles: every move adds a hole, so a position can never come back, and the game lasts at most 56 moves per side. And there are no captures: every move is "quiet", so the engine cannot recognise a good move statically as a chess engine recognises a capture. Space is everything, and a move that walls off a region of free squares for one's own pieces is often decisive.

      The engine works with bitboards: one 64-bit integer per kind of square, bit s for square s (a1 = 0, b1 = 1, …, h8 = 63). A move is stored in 16 bits as to × 64 + from. Playing it toggles two bits of the mover's bitboard, sets the hole and counts the point:

      The moves of a piece are its queen attacks through the occupied squares (pieces and holes), found in one table lookup with magic bitboards (attacks_bb), restricted to the free squares. The game value the search manipulates is an integer for the side to move: the network's value is scaled to ±30000 (WIN), and a finished game is worth ±(WIN + score difference), so that a real win always beats a position that only looks good.

      2Search foundations

      2.1Negamax and alpha-beta, fail-soft

      Negamax. A two-player zero-sum game can be searched with one function: the value of a position for the side to move is the maximum, over its moves, of minus the value of the child for the opponent. v(p) = max over m of −v(p after m). At the horizon (depth 0) the network gives the value.

      Alpha-beta. The function also receives a window (α, β): α is what the side to move is already sure to get elsewhere, β what the opponent is already sure to concede elsewhere. As soon as one move reaches β, the opponent will never allow this position, and the remaining moves need not be searched: a beta cutoff. With a perfect move order alpha-beta visits about the square root of the nodes of plain minimax, which is why so much of the engine is about ordering moves well.

      Fail-soft. The value returned is the best value found, even outside the window, not α or β themselves. It is exact when α < v < β, an upper bound when v ≤ α (every move failed low), and a lower bound when v ≥ β (a move cut). The extra precision feeds the transposition table and the aspiration windows.

      2.2Iterative deepening and adaptive aspiration windows

      Iterative deepening. The engine does not search to a fixed depth. It searches depth 1, then 2, then 3, until the clock stops it. The shallow searches cost little and fill the transposition table with best moves, which order the next, deeper search so well that the total costs less than one deep search from scratch. When the clock stops an iteration, its best move is kept if it was completely searched: the first move tried is always the previous best, so a different move that finished first had beaten it.

      Aspiration windows. The value at depth d is usually close to the value at depth d − 1. From depth 4 on, the root is searched with a narrow window (v − δ, v + δ) around the previous value instead of (−∞, +∞). A narrow window cuts much more. If the result falls outside (a fail low or a fail high) the root is searched again with the window widened on that side.

      Adaptive δ. With a fixed δ = 300 half the iterations failed: the value of Yolah positions moves a lot from one depth to the next (median change about 630, 90th percentile about 4600, on a scale where ±30000 is a sure result). So δ is k = 1.25 times the mean change of value between consecutive depths that this thread has seen, a decaying mean (factor 0.9 per iteration) kept from one move of the game to the next, never below 300. After a fail low, β comes down to the middle of the old window and α goes to v − δ; after a fail high, β goes to v + δ; δ then grows by half.

      One depth with aspiration windows (illustrative values)

      Note how a fail-soft value that fails low often sits right on the old bound: it only says "at most α", so re-centring on it moves the window by less than one might hope, and the next attempt can fail again. Measured on the bench at 1 s/move: 23 % of the root attempts fail, and 20 % of the nodes are spent in failed attempts.

      2.3The root and its move order

      The root is searched by its own function, root_search. It differs from an inner node in three ways: it returns the best move, it keeps its list of moves from one iteration to the next, and it reorders that list after each search. After a completed search the best move goes first and the others are sorted by the number of nodes their subtree took: a move that needed many nodes to be refuted came close, and is a good candidate to become the best at the next depth. (Their values cannot be used: with PVS every move but the best only has an upper bound from a null window.)

      The root fix (campaign A2) handles the failed attempts. After a fail low no move beat α, so nothing was learnt about the order and the previous best stays first; before the fix, sorting by node counts alone could put a quickly refuted secondary move first, and the clock could then stop the next attempt with that move in hand. After a fail high only the new best move comes to the front. And the node counts are summed over all the attempts of the same depth. Measured: +9.8 Elo [+3.1, +16.5] at 1 s.

      2.4One move: reduced search, null window, full window

      Every child is searched through search_move, which tries three searches, from the cheapest, and stops as soon as one settles the question.

      1. Late move reduction. A move far down the ordered list is first searched at a reduced depth (section 3.7 gives the reduction). If it does not beat α, it is believed bad and that is all it costs.
      2. Null window (PVS). Every move after the first is then searched with the window (α, α + 1). That search only answers "is this move better than α?", and it cuts far more than a full window. Since the first move is usually the best, the answer is usually no.
      3. Full window. Only when the null window says yes, with α < v < β, is the move searched again with (α, β) to get its exact value. The first move of a node goes directly to this search.

      Nodes searched with a null window are called non-PV nodes; the few nodes on the principal variation, with an open window, are PV nodes. All the risky pruning of section 3 happens at non-PV nodes only.

      3One node of negamax, step by step

      negamax is where nearly all the time goes. Its steps are presented in the order the code runs them. Each step either returns at once or passes to the next; the move loop at the end is reached only by nodes that nothing could settle more cheaply.

      3.1Finished game and table probe

      A finished game has an exact value: the score difference, pushed beyond any evaluation by WIN. Then the transposition table is probed (section 5 describes it). An entry gives an interval [lower, upper] that contains the true value, proven by a search of some depth. If that search was at least as deep as the one asked, the entry can answer at once: a lower bound ≥ β is a cutoff, an upper bound ≤ α is a fail low, and an exact value is the answer.

      No bound cuts at PV nodes (option tt cut pv off). Most bounds in the table come from null-window searches, with all their pruning and reductions. Letting a PV node return such a bound lets an approximate number climb to the root and decide the move. At PV nodes the final player only accepts an exact value or a proven game result, and otherwise searches; the entry's move is still used to order the moves. Stockfish goes further and never cuts at PV nodes. Measured: about +10 Elo on top of the root fix and the LMR change, in indirect comparisons (+2.2 in a direct match), with 9 % more nodes.

      3.2The horizon

      At depth 0 the value is the network's, through evaluate (section 7), which first looks in the evaluation cache. There is no quiescence search: Yolah has no captures, so no move is "tactical" in the chess sense, and the depth-0 value is taken as it is. Leaf values are not stored in the transposition table.

      3.3Static value and reverse futility pruning

      From here on, the pruning steps only apply at non-PV nodes (null window: the question is only "is this node ≥ β?") and never near a proven result. They all rely on the static value: the network's value of the node itself, before any search below it. With lazy accumulators and the evaluation cache it is cheap, and with the final settings it is computed at every prunable node (the RFP, proxy and MPC depth ranges cover every depth).

      Reverse futility pruning (also called "static null move"). If at depth ≤ 4 the static value exceeds β by a margin of 3000 per ply of depth, a shallow search would hardly bring it back below β: the node returns its static value. On the value scale, 3000 is a tenth of a sure win. Measured when it was introduced: +76 Elo.

      3.4Multi-ProbCut

      Multi-ProbCut (Buro, from Othello) predicts the result of a deep search from a shallow one. At a non-PV node of depth d ≥ 5, the same position is searched at depth d' = 40 % of d with a null window placed at β + margin. If even that shallow search clears β by the margin, the deep search would almost surely reach β too: the node cuts and returns β. The same is done downwards against α − margin (fail low, returns α). Buro fits the margin per pair of depths with a regression; here it is 4000 + 500 per ply of depth − d', set by matches as Stockfish sets its margins. The test is only tried when the static value is already on the right side of the window, as in Egaroucid. Measured: +57 Elo over no MPC at 1 s.

      3.5Staged move generation

      The table's move is the best move of an earlier search of this position. It often cuts at once, and then the other moves are never needed. So it is searched first, before the other moves are even generated; they are generated and scored only if it does not cut (stage 2, at i = 1 in the loop). A table move can be illegal (two positions sharing hash bits), so is_legal checks it: the piece must be on the origin and the destination reachable by a queen move. In pure alpha-beta the tree is the same as without stages; with reductions the other moves are scored after the table's move was searched, with fresher killers and history (−4 % nodes, −6 % time).

      The proxy cut of the next section needs the full list: when it runs, it generates and scores the moves itself, and the loop then starts with the full list.

      3.6The proxy cut

      The null move of chess engines asks "even if I pass, am I still ≥ β?". It assumes that passing is worse than the best move, which is false in a zugzwang, and Yolah is full of them: every move spoils some of one's own space. Measured: −81 Elo, so it is off.

      The proxy cut keeps the idea without the flaw. Instead of a pass it plays a real move m, an ordinary one (the best-scored move that is neither the table's move, a killer nor the countermove), and searches it at a reduced depth with a null window at β. The best move is at least as good as any move:

      value(best) ≥ value(m) so value(m) ≥ β ⇒ value(best) ≥ β

      In a zugzwang every move is bad, the test fails, and nothing is cut wrongly. The only approximation is the reduced depth, depth − 1 − (3 + depth/4 − 1). It is tried at non-PV nodes of depth ≥ 4 whose static value is already ≥ β. Measured: +47 Elo at 0.2 s, +59 at 1 s when introduced; after MPC was tuned it still adds about +8.

      3.7The move loop: late move pruning and late move reductions

      The moves are taken one at a time, the best-scored remaining one first (a selection step, pick_move: most nodes cut after one or two moves, so sorting the whole list would be wasted work).

      Late move pruning. At non-PV nodes of depth ≤ 3, once 4 + depth² moves have been searched (5, 8 and 13 at depths 1, 2, 3) and one of them does not lose, the remaining moves, the worst ordered, are not searched at all. Measured: +35 Elo.

      Late move reductions. With a good order the best move is almost always among the first. The later a move comes, the less likely it is to matter, and the deeper the node, the more a full search of it costs. So move number i (from 0) at a node of depth d is first searched at a reduced depth, in plies:

      r = 1.25 + ln(d) · ln(i + 1) / 1.5 (table lmr_table, in 1/1024 of a ply) − 1 at a PV node − 1 for a killer or the countermove − history / 8192 (between −2 and +2) r is truncated to whole plies, kept in [0, depth − 2]; never for the first move or at depth < 3.

      A move with a good history (it often cut elsewhere) is reduced less, one with a bad history more. Since campaign A2 the reduction reads the history alone: the move score of section 4 also contains a territory term at deep nodes, which used to leak into the reduction (option lmr territory off, +6.5 Elo alone and +12.5 with the root fix).       3.8The beta cutoff: table, killers, history, countermove

      When a move reaches β the node stops, and the search learns from it in four places:

      • the table gets a lower bound and the cutting move (section 5);
      • the move becomes the first killer of this ply (the previous first killer becomes the second): a move that refuted one position often refutes its siblings too;
      • the history of the cutting move goes up by a bonus that grows with the depth, min(16 d² + 32 d, 2000), and the history of every move tried before it goes down by the same amount;
      • the move becomes the countermove of the opponent's last move: the reply that refuted it.

      The history uses a "gravity" update, h += bonus − h · |bonus| / 16384: the closer h is to ±16384, the smaller its moves in that direction, so h stays bounded and recent cutoffs weigh more than old ones. At each new move of the game the whole table is halved: what was learnt during the previous moves still helps, but less and less.

      4Move ordering

      Alpha-beta is only as good as its move order: a cutoff on the first move skips all the others. Yolah has no captures, so nothing recognises a good move statically; the order learns from the search itself, and, at deep nodes, from a cheap territory estimate.

      4.1Scores and selection

      Each move gets a score, the highest searched first:

      RankMoveScore

      The special scores are far above anything the history and the territory term can reach, so the order between the tiers never changes; within the last tier, a gain of one square of territory is worth 512 points of history. The territory term costs about a hundred nanoseconds per move, so it is only computed at nodes of depth ≥ 4: they are few, and a good order there saves the most. Measured: +36 Elo at 0.2 s.

      4.2The territory term: influence

      territory_after(m) plays the move on bitboards (the piece leaves its square, which becomes a hole, and lands on the destination) and measures who controls the free squares. The measure is the influence: both sides flood the free squares one king step at a time, simultaneously. A square reached by both at the same step is neutral, and neutrality spreads too, blocking both floods. The result is (my squares) − (his squares). It is the "t2" territory of Amazons programs.

      The code works on whole bitboards at once. expand_king(b) adds the 8 neighbours of every square of b in five operations: the row first (b and its shifts one file east and west, masked so that nothing wraps from the h-file to the a-file), then that row one rank up and one rank down. The fronts only hold the squares reached at this step, so every square is visited once, and the loop stops when no front can advance. Step through it on a position from the middle of a game:

      5The transposition table

      The same position is reached by many move orders (a then b, or b then a), and iterative deepening searches the same positions again at every depth. The transposition table remembers, for each position searched, what the search proved about its value and which move was best. The final player uses SearchTable, a table designed for Yolah (option yolah table), 200 MB.

      5.1Zobrist hashing

      Each position gets a 64-bit key: the XOR of one random number per (square, content) pair, content being black, white, hole or free, plus one number when white is to move. A move changes four (square, content) pairs, so the child's key is the parent's XOR five numbers: no need to rehash the board. search_move computes it before playing the move and starts loading the child's table entry into the cache right away (prefetch), so that the memory access overlaps with the work in between.

      5.2Entries, clusters, replacement

      A chess table entry keeps one value and a bound type. With PVS a position often gets a lower bound (a null-window search that cut) and later an upper bound (one that failed low), and each store erased the other. A SearchTable entry keeps both bounds, proven by searches of the same depth, and merges them. Entries are 16 bytes, grouped by four into 64-byte clusters aligned on a cache line, so a probe touches one line. The low bits of the hash choose the cluster, and bits 63–16 are kept in the entry to check the position. The 200 MB asked for become the largest power of two of clusters that fits: 221 clusters, 128 MB, 8.4 million entries.

      Replacement. Yolah has no cycles and a free square never comes back, so a position with more free squares than the current root can never be reached again: its entry is garbage for sure. Each entry keeps the number of free squares of its position; when a cluster is full, such entries go first, then the shallowest one. (Chess tables approximate the same thing with generation counters.)

      5.3Storing a result: the merge

      A search of depth d with the window (α, β) returns a fail-soft value v: an upper bound if v ≤ α, a lower bound if v ≥ β, both in between. store turns that into an interval and combines it with what the entry already holds:

      • a deeper result replaces the bounds (the best move is kept if the new result has none);
      • a shallower result changes nothing (it only brings a move if there was none);
      • a result of the same depth is merged: both bounds are true, the interval can only shrink. Except that reductions and pruning make searches not perfectly consistent with each other: if the bounds cross, the new result alone is kept. On a recorded game at depth 9 this happens in 971 of 16,578 stores.

      6Several threads: lazy SMP

      The matches of the search campaigns give each player one thread, so that many games run side by side on a cluster node. In the tournament against the MCTS players it gets 16 threads (option nb threads). It then uses lazy SMP, the parallel search of Stockfish and of most modern engines: every thread runs the whole iterative deepening of section 2 on the same root, and the threads cooperate only through the transposition table. There is no splitting of the tree, no message between threads, no lock. Nothing in sections 2 to 5 changes: each thread runs exactly the code described there.

      6.1What the threads share, and what they do not

      A thread that finishes a subtree stores its result in the table. Another thread that reaches the same position, by the same line or by a transposition, finds the entry and cuts at once, or at least gets the best move to try first. With several threads searching the same tree, each one constantly finds work already done by the others, and pushes ahead of them.

      If the threads also shared their move ordering, they would all walk the same tree in the same order and mostly duplicate each other. They do not: each thread has its own history, countermoves, killers, root move order and aspiration statistics (Worker, kept between the moves of the game), and its own accumulators (Search, one search). Their orders drift apart quickly, so at any moment they are looking at different parts of the tree, and the table lets each benefit from what the others proved. The evaluation cache (section 7.1) is shared too.

      search builds one Search per thread, computes each root accumulator, starts the helpers, and runs the main thread's iterative deepening itself. When the main thread stops (the clock, or the maximum depth), it raises the shared stop flag, which every thread reads at each node, and the helpers return within a few microseconds.

      6.2Staggered depths

      Different move orders are not enough on their own: threads that all search depth 12 at the same moment still overlap a lot near the root. So the helpers skip some depths, each with its own pattern, the scheme of Stockfish's lazy SMP before 2018. Thread i skips depth d when (d + phase) / size is odd, with a (size, phase) pair per thread from two small tables; the main thread never skips. While the main thread works on depth d, some helpers are already on d + 1 or d + 2: they fill the table with deeper results, which the main thread then finds when it gets there.       6.3No locks

      Threads read and write the table at every node; a lock per entry would cost more than it saves. So the table is written without locks, and two threads may write the same 16-byte entry at the same moment, leaving a torn entry: half of one store, half of another. This is rare, and the search is built to survive it, as it already survives two positions that share the same key bits:

      • the key check (bits 63–16 of the hash) rejects most torn entries;
      • a table move is never played blindly: is_legal checks that the side to move has a piece on the origin and that the destination is free and reachable through free squares, before the move is searched first (section 3.5); a killer is checked the same way before it serves as the proxy cut's witness (section 3.6);
      • a wrong bound can at worst cut one node wrongly, as a hash collision would; it does not crash anything.

      The evaluation cache has no such problem: each entry is one 64-bit word, key and value together, read and written by single atomic operations (section 7.1). The stop flag is an std::atomic_bool read with relaxed ordering.

      6.4The move played

      When all threads have stopped, the move played is the one of the thread that completed the deepest iteration, the main thread on ties. A helper that skipped ahead may well have finished depth d + 1 while the main thread was still in depth d.

      What it buys. On the bench positions at one second per move, one thread per physical core (i7-12700K, the 126 positions that use the whole second): 1 thread visits 1.3 million nodes per second, 4 threads 5.1 million, 8 threads 8.2 million in total. Most of these extra nodes are overlap, but not all: the depth of the move played goes from a median of 20 to 21 with 4 threads and 22 with 8 (opening 18 → 20, middle game 21 → 23); with 4 threads it is deeper in 100 positions out of 126 and shallower in 6. In matches, an early version of this player with 4 threads scored 61.8 % against itself with 1 thread, about +84 Elo (section 10).

      7Evaluation inside the search

      Most nodes are leaves or prunable nodes that need the network's value. Two mechanisms make that value cheap before the network itself runs: a cache of leaf values, and accumulators that are only brought up to date when a value is actually needed.

      7.1The evaluation cache

      A leaf reached again by another move order takes its value from a cache of 220 entries (8 MB) indexed by the low bits of the hash, the newest value winning. Each entry is one 64-bit word, read and written atomically, so a torn entry (the key of one position with the value of another) is impossible even with several threads: bits 63–17 hold the key, bits 16–1 the value, bit 0 says "used". Of the 64 − 20 = 44 key bits above the index, all really check the position: a wrong value about once in 1.8 · 1013 probes. At 1 s per move, 36 % of the leaf values come from the cache (bench, 209 positions).

      7.2Lazy accumulators

      The network's first layer (section 8) is a sum of weight rows, one per feature of the position: the accumulator, 2 × 1024 int16 numbers. A move changes three features per point of view (the piece leaves its square, arrives on another, the origin becomes a hole), so a child's accumulator is the parent's plus or minus three rows of 1024 numbers per view, much cheaper than a full computation, which adds one row per piece and per hole.

      Updating the accumulator at every move searched would waste work on children that never need a value: answered by the table, finished games, inner nodes. Instead the search keeps a stack of accumulators, one per ply of the current line, each with a "valid" flag. search_move only marks the child's accumulator invalid. When a value is needed, raw_network_value walks up the line to the last valid accumulator, then down again, one fused pass per ply. A parent's accumulator is never modified, so there is nothing to undo.

      The accumulator stack along the current line

      The inner loop of update has no dependency between iterations and __restrict pointers, so the compiler vectorises it with AVX2 (checked in the binary): 16 int16 lanes per instruction, the int8 weights widened to int16 by vpmovsxbw, then vpaddw / vpsubw; 1024 / 16 = 64 iterations per view. The int16 sums may wrap around, which is harmless: wrapping addition is associative, so the order of the updates does not matter and the result is bit for bit that of a computation from scratch.

      8The NNUE network

      NNUE ("efficiently updatable neural network") is the design of the Shogi and Stockfish evaluation networks: a very wide first layer whose sum is updated incrementally move by move (the accumulator of section 7.2), followed by a few small dense layers computed with 8-bit integers and SIMD instructions. The final player's network is nnue_persp_k8_them_g046_qat_az20: perspective inputs, k8 = 8 phase heads, them = the second layer reads both points of view, g046 = three groups of hand-made space features, qat = trained quantization-aware, az20 = 20 epochs distilled from the AlphaZero network.

      8.2Points of view and phase heads

      Inputs. The network does not know the colours. It sees the position from a point of view: 192 binary inputs, my pieces (rows 0–63), his pieces (64–127), the holes (128–191). There are two points of view, one per colour, and both accumulators are kept up to date. The white view is mirrored a ↔ h so that both colours start from the same squares (black starts on a1, h8, d5, e4, white on h1, a8, e5, d4) and share the weights. With the squares numbered most significant bit first, as in the training cache, the row of square sq is 63 − sq for black and (63 − sq) ^ 7 for white: XOR with 7 flips the file.

      Us and them. The value is for the side to move: the second layer reads the clipped accumulator of the side to move ("us") and then that of the other side ("them"), always in this order. In campaign P1 the perspective network reading both views beat a fairly retrained copy of the old 193-input network by +68 Elo, while the same network reading "us" alone lost 75.

      Phase heads. A Yolah position at 10 holes and one at 45 holes need different judgement. The number of holes (one per move played) chooses one of 8 heads: bucket = min(7, holes · 8 / 57), so heads 0–7 cover about 7 holes each. Each head has its own fc2, fc3 and value weights; fc1 is shared. Only the head of the position is computed.

      8.3The ten space features

      The first layer only sees squares; mobility, territory and regions are global properties it has trouble learning. So the second layer also reads ten numbers computed from the position, for the side to move then for the other side, each an integer clamped to [0, 64]:

      Columns (us, them)FeatureMeaning
      1, 9Q1free squares within 1 queen move of my pieces (sliding through free squares)
      2, 10Q2free squares within 2 queen moves
      3, 11Q3free squares within 3 queen moves
      4, 12QFIRSTfree squares I reach in strictly fewer queen moves than the other side
      16, 17INFLfree squares I own by influence (king-step flood, section 4.2)

      They were chosen by an ablation over 92 candidate columns and by matches (campaigns P3 to P7): this group (0x46 = queen distance, queen first, influence) gave the best network. In the network a feature enters as value / 64; in C++ the int8 at scale 64 is the integer, so the quantized network sees exactly what the float one was trained on.       Queen distance levels and the ten inputs

      The queen levels are computed for all pieces at once with an occluded fill (Kogge-Stone): in each of the 8 directions, a whole set of squares slides as far as the free squares allow in 3 doubling steps (1, then 2, then 4 squares), whatever the number of squares in the set. Each level is the union of the 8 slides of the previous level, minus what was already reached.

      8.5The forward pass in C++

      8.6SIMD: the dense product

      AVX2 registers hold 256 bits: 32 bytes, 16 int16 or 8 int32. The product of an int8 matrix by a byte vector uses three instructions, the core of every NNUE:

      IntrinsicInstructionWhat it does
      _mm256_maddubs_epi16(a, b)vpmaddubsw32 unsigned bytes × 32 signed bytes, adjacent products added in pairs → 16 int16 (saturating)
      _mm256_madd_epi16(p, 1)vpmaddwd16 int16 × 1, adjacent pairs added → 8 int32: each lane now holds the sum of 4 products
      _mm256_add_epi32vpadddaccumulate into 8 int32 lanes
      _mm256_dpbusd_epi32vpdpbusd (AVX-VNNI)the three in one, without saturation; used only when USE_VNNI is defined, which the cluster CPUs (Broadwell) lack
      _mm256_hadd_epi32vphadddhorizontal adds of adjacent int32 pairs, within each 128-bit half
      _mm256_srai_epi32, min/maxvpsrad, vpminsd, vpmaxsdthe >> 6 and the clamp to [0, 64]
      _mm_packs_epi32, _mm_packs_epi16vpackssdw, vpacksswbnarrow 8 int32 to 8 int16 to 8 bytes

      Saturation cannot happen in maddubs here: an activation is at most 64 and a weight at most 127 in absolute value, so a pair of products is at most 2 · 64 · 127 = 16,256 < 32,767. The dense matvec computes 8 outputs at a time: 8 accumulator registers, one per output row, each fed by every 32-byte chunk of the input; then a tree of horizontal adds turns the 8 registers into one register holding the 8 totals.       8.7SIMD: the sparse product

      fc2 is the expensive layer: 2080 inputs × 64 outputs = 133,120 multiplications per evaluation. But h1 is mostly zero: a clipped accumulator is 0 whenever the sum is negative (with the older 193 network, 87 % of the values and 59 % of the groups of 4 values were zero). A zero input adds nothing, so sparse_nnue::matvec multiplies only the groups of 4 inputs that contain a non-zero byte. Groups of 4 because one maddubs + madd multiplies and adds 4 bytes per 32-bit lane.

      1. Find the non-zero groups, 8 at a time. Load 32 bytes of h1 (8 groups), compare each 32-bit lane with zero (cmpeq_epi32), and gather the 8 comparison results into an 8-bit mask (movemask_ps, one bit per lane). A 256-entry table gives, for each mask, the positions of its set bits; they are written 8 at a time to the list of group indices, and the list grows by the number of set bits. No branch: a loop over the bits mispredicts about once per 32 bytes, which cost more than the multiplications it saved.
      2. Multiply only those groups. The weights were laid out at load time by group: block g holds the 4 columns 4g…4g+3 for all 64 outputs, 256 contiguous bytes, lane l of register o holding the 4 weights of output 8o + l. The 4 bytes of the group are broadcast to all 8 lanes (set1_epi32), so each output accumulates in its own lane, and no horizontal add is needed at the end.
      3. Two groups per madd. Without VNNI, the maddubs results of two groups are added in 16 bits before a single madd: 2 · 2 · 64 · 127 = 32,512 still fits in an int16.

      The result is exactly the dense product's (integer sums, and the skipped groups add zero). Measured when introduced: value() −34 %, search time −21 %, +35 Elo at 1 s.

      9Training the network

      The network is not trained on game results alone. It is distilled: a large, slow, accurate network, the teacher, labels every training position with its value, and the small network learns to reproduce those values. The teacher is the value head of the AlphaZero ResNet trained by self-play, a network far too slow for alpha-beta but much less noisy than a game result.

      9.1Data and labels

      • Positions. 988,083,432 positions from the games of data/games, encoded once by preprocess_nnue.py into a memory-mapped cache: 193 bytes per position (64 black, 64 white, 64 holes, 1 side to move) and the game result z ∈ {−1, 0, +1} for the side to move.
      • Teacher values. relabel_teacher.sh ran the AlphaZero 256 network (az_00237568) on every position, one GPU, 59,938 s, and stored its value vt as float16. Against the game results, its mean squared error is 0.250, slightly better than the supervised ResNet used before (0.256), and much better in the middle game (0.285 against 0.322).
      • Space features. space_features compute-all precomputed the 92 candidate columns of every position (one byte each); the trainer appends the 10 columns of group 0x46 to each batch.
      • Split. The first 95 % of the positions train, the last 5 % validate. Positions are read in chunks of 4,194,304; the chunk order and the order inside each chunk are shuffled every epoch.

      9.2The network in PyTorch

      The cache stores colours (black, white, holes, turn). perspective() converts each batch on the GPU into the two views: the black view is the cache row as it is, the white view swaps the piece planes and mirrors every square (i ^ 7). "Us" is the view of the side to move. Every head is computed for every position, and gather keeps the right one; the cost is small next to fc1.

      9.3Quantization-aware training

      A network trained in float and rounded afterwards loses accuracy to the rounding: about 0.04 of mean absolute error on the value, with a different random loss for every training run (campaign P6 found that one epoch more or less could change the rounded network's error by more than five epochs of training improved it). Quantization-aware training removes the gap. The forward pass computes exactly what the C++ computes: weights rounded to the int8 grid, biases to the int16 grid, the >> 6 as a floor to the 1/64 grid. Rounding has no useful derivative, so the backward pass treats it as the identity (the straight-through estimator): the gradient updates the float weights, whose rounded version is what the network uses. The network learns weights whose rounded version is good. Checked: the PyTorch QAT forward and the C++ values agree exactly (maximum error 0). Measured in campaign P7: +21 Elo at 0.2 s and +29 at 1 s over the same network trained without it, at equal budget.

      9.4The training loop

      The loss pulls the student towards the teacher and keeps the game result as an anchor, so that the student does not inherit all of the teacher's systematic errors:

      L = 0.8 · MSE(v_student, v_teacher) + 0.2 · MSE(v_student, z)

      Settings of the final network (campaign P7): initialised from the older distilled 193-input network (fc1 without its turn row, each head a copy of its fc2 to fc4, the "them" half and the space columns of fc2 at zero, so that it starts with the old network's values on positions with black to move); 20 epochs; Adam, learning rate 3·10−4 with a cosine decay to 10−5; batches of 1024 positions; float32 (the bfloat16 used for other networks cannot hold the 1/64 grid exactly); PyTorch DDP and torch.compile. After every step the trunk weights are clamped to ±127/64 so that they stay representable as int8; the value heads are free (they stay float in C++). Final validation error against the teacher: 0.0764.

      9.5From PyTorch to the C++ weights file

      export_value_nets.py --persp writes a text file: a header (PERSPC, K = 8, them = 1, the sizes 1024, 64, 32, then the 10 space columns), then every matrix as integers at the scales of section 8.4, the value heads as floats. The C++ loader reads it, transposes fc1 into one row of 1024 per input (the layout the accumulator needs), pads each fc2 row from 2058 to 2080 columns, and builds the grouped copy of fc2 for the sparse product. Because the network was trained quantization-aware, the rounding of the export is the rounding the training already used.
