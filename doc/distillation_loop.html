    Yolah Distillation Loop Internals

    How the two Yolah players improve each other, round after round: the minimax dev player plays games and labels the positions with its search, the value/policy ResNet of the MCTS player learns from them, the ResNet becomes the teacher of the NNUE, and the dev player plays the next round with the new NNUE. Every stage is shown with its code and its targets.

    200 kgames of the dev player per round
    650 ksearch nodes per move (0.5 s on an i7)
    ~210labelled positions per game, tree nodes included
    ~100 Mpositions in a round's training cache
    Stopped after round 0. The ResNet is now improved by the generations loop, nnue/az_gen_loop.sh: see az_gen_loop.html. This page describes the distillation loop as it ran; section 7 of the new page gives its results.
    Contents

      1The loop at a glance

      Two players share one game. The dev player is a minimax search with a small NNUE network at the leaves; it searches to depth 20 in half a second. The MCTS player is guided by a large value/policy ResNet; it sees few positions but judges each one better. Until now each player was trained on its own: the NNUE by distillation of a fixed ResNet, the ResNet by AlphaZero self-play, which gained about 17 Elo over weeks of GPU time.

      The distillation loop connects them. A deep search is a much better label than the result of a self-play game: it is precise for the position itself, it is available for every position the search looked at, and the dev player produces it cheaply on CPUs. Each round, the dev player's games label tens of millions of positions; the ResNet learns from these labels; the ResNet, now better, re-labels the positions as the NNUE's teacher; the NNUE learns, and the dev player plays the next round with it. Both players are measured after each round, against the previous round and against round 0.

      1.1One round

      Round r starts from the networks NNUEr and ResNetr and ends with NNUEr+1 and ResNetr+1. Round 0 starts from the NNUE g046 (the network of the final dev player) and the latest network of the AlphaZero 256 run.

      2Generating the games

      The generator selfplay_label plays games of the dev player against itself, one game per thread, one thread per physical core. Each game writes all its records in one block at the end.

      2.1A node limit, not a clock

      A search limited by time reaches different depths on different machines: the same task would produce better labels on a fast node than on a slow one. The option "max nodes" stops the search after a fixed number of nodes of the main thread instead. With 650 000 nodes, a move takes 0.5 s on an i7-12700K and reaches the same depth on every machine; only the time changes. The generator also sets one search thread per game and a 64 MB table.

      2.2Openings

      A search with a node limit and a cleared table is deterministic: the same start gives the same game. The diversity comes from the start alone. Each game takes one of the 4000 balanced openings of the book (6 plies each), then plays 2 random plies. The game number seeds both, so a game played again after an interruption is the same game. There are millions of possible starts; among 200 000 games, about 1 % repeat a start.

      2.3The record

      Every labelled position is a 40-byte record: the position (three bitboards, the ply, the scores), the search's value and depth, a move, its kind, the game's result and the exact result.

      2.4Positions from inside the search

      A game gives about 47 positions where the player searched. The search itself evaluated millions of others, and some of them carry a label as good as the root's. With "record depth" set and a recorder attached, the main thread records a node at the end of negamax when three conditions hold:

      • the node is a PV node: its window was wider than a null window (β − α > 1);
      • its value is exact: strictly inside the window (α < v < β), not a bound from a cutoff;
      • it was searched to a remaining depth of at least 10 plies, and the search was not stopped meanwhile.

      Such a node has a value searched almost as deep as the root's, and a best move.

      After each search the generator shuffles the recorded nodes and keeps up to 8 of them, each position at most once per game (a hash set). Finished positions are skipped. In practice a search yields about 4.4 such nodes on average, about 206 per game.

      2.5The result and the exact result

      When the game is over, every record gets the result z for its side to move. Every record with at most 22 free squares also goes to the endgame solver, with a watchdog thread that stops it after 300 ms; a solved position gets its exact result (win, draw or loss), the others keep EXACT_UNKNOWN. About 35 % of the records are solved, and fewer than 0.3 % run out of time.

      2.6Writing and resuming

      Each game is written with one fwrite under a mutex, then flushed. A task stopped by its time limit or by a preemption starts again where it was: the last game of the file is the only one that can be incomplete, so it is cut off and played again, under the same number and therefore identically.

      2.7Speed

      With a fixed node count, the time per game measures the CPU. One game per physical core (the logical CPUs of hyperthreading are not used):

      3The training cache

      loop_prepare.py turns the records into a cache in the layout of preprocess_nnue.py, so that the labelling script, the space features and the NNUE trainer read it as they read every other cache, plus a few files of the loop.

      3.2Tree nodes that the game played

      About 19 % of the tree nodes are positions the game reached later: the search predicted the line, and the game followed it. Each is then twice in the records, once as a tree node with a shallower search, once as a game position. The tree copy is dropped; the game's record is kept.

      3.3When the game's result is not the position's

      For a position of the game, z is the result of the game played from it. For a tree node off the game's path, z is the result of another position: the game never went there. The measure, on 192 games where the solver gives the truth (at most 22 free squares):

      Positions with a known exact resultnz = exactMSE(z, exact)MSE(s, exact)

      Off the path, z is three times further from the truth than the search value, and the gap grows with the free squares and the distance from the root. These nodes are 81 % of the tree nodes. zmask.u1 marks them: 0 for a tree node off the path without an exact result. Both trainers then leave z out on those rows. A solved tree node takes z = the exact result and keeps zmask = 1.

      3.4A window of rounds

      Training on the games of one round only would make each network forget what the previous rounds taught it. The cache of round r holds three sources:

      • all the games of round r;
      • half of the games of each of the 2 previous rounds, drawn at random, whole games;
      • positions of cache_az256, the old distillation cache: positions of the engine games of data/games with their real result z and, as their label, the value of the AlphaZero 256 ResNet. 50 M at round 0, then 50 · (1 − r/3) M: 33 M, 17 M, and none from round 3. They are taken in random blocks of 4096 consecutive positions.

      The games of a round are deleted when the round leaves the window; the cache of a round is deleted as soon as the round is trained.

      The rows are written by blocks of 4096: blocks of new records and old blocks, in a random order. The trainers read the cache by chunks of consecutive rows and keep its last 5 % for validation, so the validation set holds all the sources.

      4Improving the ResNet

      loop_resnet.py fine-tunes ResNetr on the round's cache for one epoch and exports ResNetr+1. It is the network of the MCTS player, with both its heads trained.

      4.1The targets

      PositionsValue target (MSE)Policy target (cross-entropy)
      game positions0.3 · z + 0.7 · sthe move played
      tree nodes off the path, unsolvedsthe node's best move
      solved positions (game or tree)the exact result (z and s are both exact)the move played or the best move
      old positions (cache_az256)0.3 · z + 0.7 · old labelnone

      The result z brings the truth of the whole game: noisy for one position, but unbiased. The search value s is precise for the position but biased by the NNUE that produced it. The blend keeps both. The policy target is one-hot: the search's choice. The tree nodes multiply the policy targets by five.

      4.2Training

      Each row of a batch gets one of the 8 symmetries of the board, drawn at random, and the move index goes through the same symmetry (alphazero_learn.symmetry_tables). The optimiser is AdamW (learning rate 5·10⁻⁵, weight decay 10⁻⁴, batch 1024), with a linear warm-up over 500 steps then a cosine down to a tenth, gradients clipped at 5, bf16 on the GPU. The cache is read by chunks of 4 M rows in a random order, each chunk shuffled. The exported network is the exponential average of the weights (decay 0.999).

      Before and after the epoch, the validation part gives the MSE against the value target, the MSE against z, the policy cross-entropy and the policy top-1 accuracy (resnet_log.jsonl). The export writes az_<r+1>.pt and its TorchScript .ts, the file the MCTS player loads.

      5The NNUE's teacher

      The NNUE learns from a teacher value per position. It is made in two steps, right after the ResNet's training.

      1. distill_teacher_labels.py runs ResNetr+1 on every position of the cache, old ones included: vR.
      2. loop_blend.py mixes it with the search target: teacher = ½ · vR + ½ · s, or the exact result where it is known.

      The search sees far, but through the eyes of NNUEr; the ResNet is a richer static judge, without search. The mean of the two corrects part of the bias of each. Where the exact result is known, the network should learn the truth, not an estimate of it. On the old positions, s is the old label of the AlphaZero 256 ResNet, so their teacher is the mean of the new and the old ResNet.

      The ResNet's own labels stay in teacher_resnet.f16, so the blend can be made again with another weight. blend_meta.json records the distance between the ResNet and the search, and between the ResNet and the exact results: a measure of the ResNet's errors on the truth.

      6Distilling the NNUE

      NNUEr+1 starts from NNUEr, with the same architecture (perspective network, 8 phase heads, the space features of groups 0x46), and trains for 2 epochs at a learning rate of 10⁻⁴, quantization-aware: the forward pass rounds the weights and activations as the C++ integer code does, so the exported network plays as it was trained.

      6.1The loss

      L = 0.8 · (v − teacher)² + 0.2 · (v − z)²

      A weighted sum of two squared errors has its minimum where a single squared error to the weighted mean of the targets has it: the NNUE learns the value 0.8 · teacher + 0.2 · z. With vR = 0.40 and s = 0.20, the teacher is 0.30; if the game was won (z = +1), the NNUE aims at 0.8 · 0.30 + 0.2 · 1 = 0.44.

      Where z is not the position's result (zmask = 0), the loader replaces z by the teacher. The loss becomes 0.8 · (v − teacher)² + 0.2 · (v − teacher)² = (v − teacher)²: the teacher alone.

      6.3Export

      The last epoch's checkpoint is exported by export_value_nets.py --persp into nnue.quantized.txt, the integer weights file. The dev player of round r+1 is dev_final.cfg with these weights: the search is unchanged from round to round, only the network changes.

      7Measuring the progress

      After each round both players play two matches, against the previous round and against round 0, at 1 s per move, from the balanced openings, each opening played with both colours:

      • the dev player with NNUEr+1 against NNUEr and NNUE0: 1000 pairs of games on 32 cores (yolah_tournament);
      • the MCTS player with ResNetr+1 against ResNetr and ResNet0: 400 games on a GPU, in the evaluation setting (4 threads × batch 32, alphazero_match.sh).

      loop_progress.py gathers them in progress.csv: for the NNUE, the Elo with a pentanomial interval (the pairs of games as the unit, which removes the colour's share of the noise); for the ResNet, the Elo of alphazero_match.sh. The matches against round 0 add up the rounds; the matches against the previous round say whether the last one still helped.

      8On the cluster
